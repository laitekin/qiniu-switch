01

Python 基本语法

基础语法已在本地实践过，这里集中整理思考题。

Q1Jupyter Notebook 的使用体验

Jupyter 是「所见即所得」的交互式编码：一段代码一个单元格，运行结果、图表直接显示在下面，特别适合数据分析、画图和记录实验过程。PyCharm 也内置了 Notebook 插件，两者可以配合使用。

我的看法：探索性分析用 Jupyter 很顺手；但实际项目通常规模较大、模块较多，工程化开发、调试与重构还是 PyCharm 这类 IDE 更合适。
Q2创建空列表：[] 还是 list()？

优先 []字面量直接由解释器创建列表；list() 需要先查找名字 list 再发起一次函数调用，多一步开销，写法也更长。

# python -m timeit
[]      #  ~15 ns
list()  #  ~40 ns
Q3两种字典初始化方式哪个更高效？

字面量 {...}dict({'name': 'jason', ...}) 会先创建一个字典，再调用 dict() 复制出另一个，多了不必要的操作。

d = {'name': 'jason', 'age': 20}  # ✓
d = dict({'name': 'jason'})     # ✗ 多一次拷贝
Q4列表能作为字典的键吗？

不能运行会报 TypeError: unhashable type: 'list'。字典的键必须可哈希（不可变且能比较），列表是可变对象。可以改用字符串 'education' 或元组作为键。

Q5两种字符串拼接方式哪个更优？

首先两者结果就不同：s += str(n) 不加空格，' '.join(l) 会在元素间插入空格。

性能上 join 一次性计算总长度并分配内存，大量拼接时更优；循环里反复 += 可能产生多次拷贝。

Q6大文件如何统计词频？

分块 / 逐行流式读取，避免一次性读入内存，边读边用 Counter 累加；数据量更大时可以分片统计后再合并（MapReduce 思路），或者用 bitmap 等紧凑结构降低内存。

Q7数据库连接和查询需要多个 try/except 吗？

不需要不必为每条可能出错的语句嵌套一层。用一个 try 包住整个事务，按异常类型分别处理，并在 finally 或 with 中释放连接。

Q8from m import * 与 import m 的区别

import m 把模块对象放进当前命名空间，使用时写 m.func；from m import * 把模块公开的名字直接倒进当前命名空间，容易覆盖同名变量，可读性差。

Q9异步代码中如何处理返回结果？

直接 result = await fetch()，然后顺序处理 result，比回调或手动管理 Future 更清晰。

async def main():
    result = await fetch("https://api.example.com")
    handle(result)

02

量化交易

用 Python 实现买入、卖出等交易流程，并思考行情数据与系统性能问题。

Q1高频交易和中低频交易，哪个更适合使用 Python？

中低频中低频交易更适合用 Python 完成策略开发、数据处理、回测和系统编排。高频交易对延迟及其抖动非常敏感，关键执行路径通常需要 C++ 等性能更可控的实现；Python 在高频场景中仍可用于研究和监控。

Q2能用 timestamp 代替 nonce 吗？

可以，但有条件时间戳可以作为 nonce 的值，但必须符合交易所的校验规则：

· 时间型 nonce（如 Gemini）要求与服务器时间接近；
· 递增型 nonce 要求同一 API Key 的每次请求严格递增。

同一秒内并发请求、系统时钟回拨，都会让「直接取时间戳」失败。建议用毫秒/微秒时间戳 + 单调递增保护。
Q3WebSocket 会丢包吗？订单簿爬虫该怎么办？

会TCP 保证单连接内有序，但断线重连、服务端推送丢弃都会造成消息缺失。

应用层要做探测：检查消息序列号是否连续、定期对比 checksum；一旦发现缺口，就重新拉取订单簿快照，再继续应用增量。

Q4如何用 Tick 数据生成 5 分钟、小时和日 OHLCV？

OHLCV 是一段时间内的行情摘要，也就是一根 K 线：先按时间排序，再按 5 分钟 / 1 小时 / 1 天分组，每组首笔价格 = Open，最高 = High，最低 = Low，末笔 = Close，成交量之和 = Volume。还要明确时区、窗口边界（左闭右开）以及空窗口的处理。

ohlcv = (ticks.set_index("ts").sort_index()
         .resample("5min")
         .agg({"price": "ohlc", "qty": "sum"}))
Q5ZMQ 发布者的 time.sleep(1) 移到循环末尾会怎样？

发布者启动后会立即发送第一条消息，而此时订阅者可能还没完成连接和订阅，于是最初的消息会丢失（ZMQ 的 "slow joiner" 问题）。

sleep 本质是在等连接建立，只能降低概率。可靠的做法是就绪确认（订阅者回报 ready）或消息恢复机制。
Q6如果有多个发布者，ZMQ 应该怎么做？

让每个 PUB 绑定自己的地址，由 SUB 同时 connect 多个发布者；规模较大时用 XSUB/XPUB 代理汇聚和分发。

普通发布订阅没有自动补发，关键行情仍需在消息中透传消息 ID / 序号，做缺口检查与重新同步。
Q7回测系统调用频率极高，如何降低调用代价？

· 不要每处理一个 Tick 就查一次数据库，按时间范围批量读取，在内存中连续处理；
· 为常用查询建立合适的索引；
· 对重复使用的 K 线做缓存或预聚合（Redis 等缓存组件），避免数据层的大量 IO。

Q8Django RESTful API 如何实现安全认证？

常见方案：

Session + CookieTokenJWT双 Token 刷新

双 Token：短期 Access Token 用于请求鉴权，长期 Refresh Token 用于续期，兼顾安全与体验。配合 HTTPS、权限类和限流使用。

DFS 与 BFS

回溯 vs 动态规划

BT回溯

在搜索树上做选择 → 递归 → 撤销选择，关键是保存并恢复上一步的状态，同时用剪枝减少无效分支。典型题：全排列、N 皇后、组合求和。

DP动态规划

找到状态定义和状态转移方程（如 dp[i] = max(dp[i-1], dp[i-2] + v[i])），利用重叠子问题避免重复计算。典型题：背包、最长子序列。

Clawd 小贴士 · 回溯是「试一试、不行就退回来」，动态规划是「把算过的记下来」。先写出递归，再想能不能加备忘录。

05

架构设计

本周目标：建立完整的架构知识体系。

架构设计不是简单地堆砌微服务、缓存、消息队列等技术，而是根据实际业务，找到并解决系统中最复杂的问题。

复杂度的六个来源

⚡高性能

单机性能与集群并发能力，响应时间与吞吐量。

♻高可用

通过冗余消除单点，计算高可用与存储高可用。

⇲可扩展性

预测变化、封装变化，新需求来时改动最小。

🛡安全

功能安全（防 XSS / SQL 注入）与架构安全（防火墙、隔离）。

¥成本

机器、带宽和人力成本，技术方案要算得过账。

∑数据规模

数据量从量变到质变，需要分库分表、NoSQL 等手段。

后续计划：通过实际项目练习需求分析、技术选型、架构图绘制和架构文档编写，逐步提升从发现问题、分析问题到设计并落地方案的能力。

云原生开发技术

架构设计与云原生息息相关：在 K8s 上部署时，必须结合架构设计一起考虑。

基础设施即代码（IaC）与自动化部署

MTerraform Module

面对几十上百个集群，把通用配置封装成 Module，不同环境 / 集群单独维护参数与 State，经 Git + CI/CD 统一管理。

HHelm + Argo CD

Ingress、Prometheus、Grafana 等公共组件，用 Helm 打包，Argo CD 与 ApplicationSet 实现集中管理与差异化配置（GitOps）。

⚙流水线选型

GitHub Actions 适合快速搭建简单流水线；Tekton 适合私有化与复杂流程；Operator / Crossplane 适合 K8s 体系成熟后声明式管理应用和云资源。
